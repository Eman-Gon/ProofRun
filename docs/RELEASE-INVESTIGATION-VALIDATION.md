# Release investigation validation

On September 29, 2026, an authenticated release-event submission completed a **live model and Docker investigation in 232.09 seconds** using a 300-second execution budget. The result was **skip the original release**, with two reproduced regressions and one independently verified repair candidate.

This was a separate synthetic evaluation product, generated by [the evaluation script](../scripts/evaluate-release-investigation.py). It was not a customer deployment or the registered Pydantic nickname fixture. The registry supplied a general response-preservation requirement, startup/test commands, protected test paths and immutable images. It supplied no failing request, bug location, or prepared repair to the agent.

## What executed

- Exact baseline and candidate Git snapshots, with recorded source manifests.
- Authenticated target discovery, deployment-event submission, duplicate-event handling, polling, and retrieval of six hash-checked artifacts.
- Seven actual OpenRouter operations using the configured `anthropic/claude-sonnet-5` model, including source inspection, generated experiments, repair proposal, and final summary. No substitute model or injected agent was used.
- Three agent-selected HTTP experiments, each repeated twice on each release in fresh Docker applications. A trusted collector ran separately in the application's isolated loopback network namespace.
- Original baseline tests, the same frozen tests against the candidate, and the candidate's current suite. The repair reran both suites and all three frozen experiments twice.

| Generated experiment | Baseline | Candidate | Harness result |
| --- | --- | --- | --- |
| Customer ID `12345` | HTTP 201, original ID | Same | Preserved control |
| Customer ID `00123` | HTTP 201, ID `00123` | HTTP 201, ID `123` | Confirmed response regression |
| Customer ID `abc-123` | HTTP 201 | HTTP 422 | Confirmed response regression |

The agent inspected the change that converted string identifiers through `int()` and proposed removing that conversion. The harness returned `verified_candidate` after the patched copy preserved all three experiments and passed both test suites. The original candidate remained `skip`. No repair was deployed.

The agent's initial hypothesis for the nonnumeric ID predicted a server error; execution instead measured HTTP 422. The final summary used the measured result. Stored hypotheses remain explicitly separate from confirmed observations and do not establish an introducing commit.

## Additional checks and limits

The final release-investigation Python suite passed **125 tests in 45.58 seconds** across the agent, runtime, investigation, API, and policy checks. An earlier broader run passed 249 checks and exposed one test timing race; that test and its adjacent deadline test now use a controlled clock. Coverage includes source/revision binding, protected tests, bad-repair rejection, unstable/incomplete observations, JSON boolean-versus-number differences, scope isolation, event conflicts, artifact tampering, deadlines and staging revision changes.

The release gateway passed 84 standalone boundary assertions and compiled against the actual DuploCloud SDK 1.0.6. The release UI production build passed, including artifact downloads and separate cause hypotheses. These checks do not establish live portal authorization or a new release-screen browser session. Concurrent optional research work has its own validation and may change the shared bundle after these source snapshots.

The service entry point also started and served authenticated configured targets without making a provider call. Actual customer staging, Crusoe hosting, and a real customer repository remain separate configuration and execution steps. Source exclusions, exact-response requirements, bounded experiment coverage, and operator-supplied image-to-release mappings still apply.

## Repeat the live evaluation

With Docker available and the existing private OpenRouter settings exported, choose a new output directory and a preloaded, trusted immutable Python image:

```bash
python3.12 scripts/evaluate-release-investigation.py \
  --output /tmp/proofrun-release-evaluation-new \
  --image sha256:REPLACE_WITH_YOUR_64_CHARACTER_IMAGE_ID \
  --budget 300 \
  --api
```

The script creates an evaluation Git repository, starts an ephemeral authenticated worker, and checks its real API. It exits zero when a regression is actually discovered and the original release is classified `skip`; a repair's separate status is retained in `evaluation.json`. It never connects to customer staging.
